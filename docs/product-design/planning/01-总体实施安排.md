# 总体实施安排：Codex 主代理 + DSH 前端子代理

> 状态：产品设计工作基线，非已实现能力清单。下文方案与验收目标受[来源与状态](../SOURCE-AND-STATUS.md)及[待决登记](../DECISION-REGISTER.md)约束；未标定的实现细节按设计建议理解，倾向和未回答均不构成最终决定。返回[文档导航](../INDEX.md)。 本文仅供后续获准开发时参考，不是本轮执行指令；阶段顺序与代理分工仍需确认。

## 1. 目标与分工

目标不是按文档顺序一次性完成所有模块，而是让几条能够独立验证的产品链路并行推进，并尽早在真实 DSH/Logseq 环境中使用。

### 主代理：Codex（负责全局一致性）

主代理负责：

- 核对当前 `main`、`codex/one-click-dsh-collaboration` 与 DSH SDK 的实际版本/接口。
- 维护共享 WorkRef、SourceRef、ReturnContext、操作结果等最小契约。
- 决定模块之间的接口和写入边界，避免重复建模。
- 审核正式 Kernel 操作和可信授权来源；不能把 Agent 自报授权当作可信来源。
- 负责合并、回归测试、真实宿主验收与最终交付。
- 处理跨模块文件、共享样式、路由、持久化和 schema 变更。

### DSH 子代理：优先承担有边界的前端工作

用户希望 DSH 子代理更多承担前端实现。适合委派的任务包括：

- Capture/Inbox 的视觉与交互实现。
- 结构历史只读 renderer 的界面实现。
- DSH 内联 Lens 条目与轻量阅读层。
- 日程拖动交互与结构图动效。
- 可插拔主题和窄屏适配。

每个子代理任务必须附带：输入文档、允许修改的文件范围、不可修改的共享接口、模拟数据/真实数据边界、必须通过的检查和交付说明。子代理不应同时改共享领域类型、Kernel API、跨模块路由或存储 schema；需要改动时先向主代理提出接口变更建议。

> 实际是否能从 Codex 通过 MCP/其他机制调用 DSH 子代理，仍需在用户的运行环境中单独验证。此安排是工作分工建议，不代表调用通道已连通。

## 2. 两条并行主线

### 主线 A：Capture → Inbox → DSH → 返回原现场

先做真实日常价值最高的链路：

1. DSH 入口呼出捕获窗并聚焦输入。
2. 保存、钉住连续记录、失败恢复、草稿保护。
3. Inbox 历史列表、搜索、双击编辑、今天/全选、归档与恢复。
4. 选中记录后带引用打开 DSH 草稿，由用户发送。
5. 保留来源、返回焦点与未发送草稿。
6. 记录从 Inbox 转成 `[想法]`、TODO、Journal 或正式对象的状态关系；第一版不强制做完整自动分类。

### 主线 B：真实工作结构历史

利用现有 Stage 快照和可核查来源，独立验证：

1. 读取真实结构快照，区分正式对象树、Logseq 来源树和代码模块图。
2. 在同一张图上播放节点、文字、父子关系、依赖和状态变化。
3. 保持大部分节点位置稳定；变化局部高亮。
4. 点击节点可打开对应版本的来源/差异。
5. 缺失历史明确显示未知；不使用今天的文本补旧帧。
6. 文字目录作为图形不可用时的完整回退。

两条主线可以并行，但在共用工作身份、来源引用和主题基础上先对齐契约。它们不应同时重写 Kernel 或建立互不兼容的 ID 系统。

## 3. 建议阶段与依赖

### P0 — 当前基线与最小契约

**主责：Codex。**

- 获取当前分支 SHA 与工作树状态，重读正式 Kernel 文档和 DSH 插槽 API。
- 对比两个分支的共同祖先、增量提交、schema 与 DSH feature 实现。
- 建立本次工作的可读状态标签：用户倾向/正式已接受/Graph 投影待处理/未知。
- 约定最小 `WorkRef`、`SourceRef`、`ReturnContext`、操作结果结构；只抽取两条主线确实共用的部分。
- 写清 Inbox 记录与 Journal 的关系、可信用户指令来源的待实现接口。

**完成条件：** 现有一键 DSH 路径能运行；共享接口有简短契约与类型检查；没有在这一阶段引入通用 workflow engine 或大量新领域实体。

### P1A — Capture / Inbox 日常闭环

**主责：DSH 前端子代理实现界面，Codex 接持久化、宿主接口、集成与验收。**

- 捕获窗首帧、钉住连续写、键盘语义、保存状态与草稿恢复。
- Inbox 紧凑列表、搜索、双击编辑、批量选择、归档/恢复。
- 带引用打开 DSH 草稿，保留原会话和返回状态。
- 处理状态先覆盖保留、考虑中、已处理/归档；正式化和 Journal 写入通过明确出口接入。

**验收：** 在真实 DSH 中，用户能不看教程快速记录、编辑、搜索、带入对话并返回；断连不丢正文；按钮与文字不形成操作面板。

### P1B — 结构历史只读体验

**主责：DSH 前端子代理负责 renderer，Codex 负责快照适配、来源和测试。**

- 使用真实 Stage 快照，不用原型模拟数据替代实际历史。
- 先完成同一张结构图的时间切换、局部变化高亮、节点来源入口。
- 加入正式对象树 / Logseq 来源树 / 代码模块图的清楚切换。
- 缺失数据、被删除来源和布局失败均有可读回退。

**验收：** 能在真实项目数据上解释某个节点何时新增/改名/移动；不能证明的历史明确标注未知；无外部写入副作用。

### P2 — DSH 内联线索、结构 Diff 与正式操作

**依赖：P0 的 SourceRef/ReturnContext，P1A 的 DSH 入口，P1B 的结构 renderer。**

- Lens 条目嵌入 DSH 对话，用户可直接讨论。
- 结构 Diff 复用同一 renderer，显示增删移动和文字变化。
- 明确用户指令与 Agent 推断的操作路径。
- 正式操作沿用 Kernel 可信来源、版本检查、幂等收据和 Graph 投影状态。
- 先支持少量清楚的操作，不建设通用审批平台。

**验收：** 明确、可信、范围内的指令不被重复审批；越界操作会停下；冲突与部分成功可恢复。

### P3 — 外部工作证据、恢复和收尾

- 在工作重入或用户请求时增量观察 Git/文件/Logseq。
- 用户可补充“这次想解决什么”，由 DSH 根据缺口动态追问。
- 共享结构图支持恢复、暂停和收尾：当前节点、上一轮变化、遗留点、下一次入口。
- 有限快照先限定到选中工作范围和可安全保存的文本；明确敏感文件与保留规则。

**验收：** DSH 外工作可进入工作记忆；观察与解释不混淆；恢复和收尾无需强制填写报告。

### P4 — 语义规划与有限领航

- 在 DSH 对话过程中展示今天/明天投入安排。
- 拖动优先，支持撤销、未完成项留在原处、待安置时段。
- 领航开始/暂停/恢复/结束与结构图对应；限定范围和停点。
- 暂不扩大正式任务自动代办权限，不写外部日历。

**验收：** 计划与正式事实分开；人类决策点会停；结束领航不自动完成 Task。

### P5 — 可插拔主题与高级交互

- 加入轻像素主题，默认仍为阅读式。
- 逐步优化图形交互、局部恢复草案和更丰富的视图。
- 只有在日常使用证明必要后，才考虑完整任务地图、自动阶段解释或更复杂的图形编辑。

## 4. 可并行任务矩阵

| 任务 | 主责 | 可委派给 DSH 子代理 | 主要依赖 | 不允许越界修改 |
|---|---|---|---|---|
| 当前代码/SDK 基线审查 | Codex | 否 | 无 | 不修改仓库，只读核查 |
| Capture 界面与钉住交互 | DSH 子代理 | 是 | Capture 行为契约 | 不改持久化 schema、Kernel |
| Inbox 列表/编辑/多选 | DSH 子代理 | 是 | CaptureRecord 与状态契约 | 不擅自增加正式对象类型 |
| DSH 草稿/返回集成 | Codex | 可委派 UI | DSH SDK 与 ReturnContext | 不把浏览当会话重绑 |
| 历史结构 renderer | DSH 子代理 | 是 | Snapshot 只读数据契约 | 不伪造旧历史、不做正式写入 |
| 历史数据适配 | Codex | 不建议并行改 | Stage 快照与来源 API | 不改快照语义而无迁移计划 |
| Lens 内联卡片 | DSH 子代理 | 是 | SourceRef 与 DSH slots | 不建立独立 Lens 仪表盘 |
| 正式写入授权桥接 | Codex | 不委派无监督实现 | Kernel/DSH 可信来源核查 | 不信任 Agent 自报 USER 来源 |
| 结构 Diff / 部分采纳 | Codex 统筹，前端可委派 | 是，限 renderer | P1B + ChangeSet 契约 | 不让布局拖动直接写 Kernel |
| 日程拖动 UI | DSH 子代理 | 是 | ScheduleAllocation 最小契约 | 不写外部日历、不改 Task 状态 |
| 主题 CSS | DSH 子代理 | 是 | 语义化 tokens | 不改变信息布局/正式语义 |
| 合并、测试、宿主验收 | Codex | 审阅可委派 | 所有任务 | 最终责任不能分散 |

## 5. 子代理任务卡模板

每次委派只包含一个可独立检查的工作包：

- **目标**：用户完成哪一个具体行为？
- **用户路径**：从哪里进入，操作后应看到什么，如何返回？
- **允许修改**：列出明确文件/目录。
- **禁止修改**：共享类型、Kernel、持久化 schema、其他代理正在编辑的文件。
- **数据边界**：哪些是真实来源，哪些是模拟数据；不得把模拟数据写入正式路径。
- **接口约定**：输入/输出类型、状态、失败语义。
- **验收**：运行哪些测试，如何手动复核真实宿主。
- **交付说明**：改了什么、运行了什么、未验证什么、已知限制、需要主代理决定什么。

## 6. 质量门槛

每个模块交回时至少提供：

1. 可运行的实现或明确标记的原型。
2. 改动文件列表与行为说明。
3. 实际执行的检查命令和结果；不得把既有文档中的测试宣称算成本次测试。
4. 未验证边界与已知问题。
5. 失败路径验证：断连、来源失效、冲突、回执未知、部分成功中适用的场景。
6. 真实 DSH/Logseq 宿主手动验收记录。

测试层次：领域语义单测 → 适配器集成 → 插件 UI 集成 → 真实宿主验证 → 适用的故障注入/性能样本。静态 HTML 通过不能替代真实宿主验收。

## 7. 不要做的事

- 不要一口气重构全部 Kernel。
- 不要让两个代理同时修改共享 schema、路由或基础样式。
- 不要先建立通用 workflow engine。
- 不要在历史中用模拟数据冒充真实项目演变。
- 不要让 DSH 子代理自行决定正式语义或权限边界。
- 不要把每个用户倾向写成最终验收条款；未决项要明确留档。
- 不要因为模块可并行就忽略整合、回归与真实宿主测试。

## 8. 后续获准开发时的首批任务建议

1. **Codex / 只读**：重新获取当前 `main`、feature 与 DSH SDK 的实际版本；检查 feature 与当前 main 是否仍可直接叠加，确认正式对象类型、commit/投影语义、可信来源入口和现有测试命令。
2. **Codex**：写出一页最小共享契约草案（WorkRef、SourceRef、ReturnContext、CaptureRecord、操作结果），仅解决 Capture 和历史两条主线的共同部分。
3. **DSH 子代理 A**：实现 Capture/Inbox 前端交互，先使用明确标注的模拟服务接口，不改持久化与 Kernel；提供键盘/窄屏/失败态检查。
4. **DSH 子代理 B**：实现只读结构历史 renderer，输入来自固定 Snapshot fixture，节点身份和历史缺口有明确呈现；不得声称 fixture 是真实仓库历史。
5. **Codex**：把 A/B 的接口合并到共享契约，接真实数据适配与 DSH 宿主；任何跨界变更先审查，不让子代理私自改共享核心。

在获得开发授权并确认接口依赖后，这五项可按依赖安排并行推进，但第 3/4 项只负责可独立验收的前端工作；P1 的真实完成条件仍由 Codex 集成与宿主验收决定。
