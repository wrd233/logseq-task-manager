# 模块需求：工作证据与结构历史

> 状态：产品设计工作基线，非已实现能力清单。下文方案与验收目标受[来源与状态](../SOURCE-AND-STATUS.md)及[待决登记](../DECISION-REGISTER.md)约束；未标定的实现细节按设计建议理解，倾向和未回答均不构成最终决定。返回[文档导航](../INDEX.md)。

## 目标

让系统理解 DSH 之外的实际工作修改，并能用真实历史结构帮助用户理解项目如何演变。阶段回顾不应要求用户手动开始/结束阶段、逐项维护或强制 Git commit。

## 证据来源

- Logseq Graph 的 Git 状态、历史和来源块。
- 工作目录的 Git 提交、分支、工作树变化与未跟踪文件。
- 在授权范围内可读的文件差异/有限快照。
- DSH 工具轨迹、测试输出和相关会话引用。
- 用户简短补充，例如“这次是为了修复恢复时丢失草稿”。

机器观察与用户解释应分开记录。比如，系统可以说“恢复逻辑与说明文件发生变化”；不能仅凭这两项变化就宣布“恢复功能已完成”。如果用户说真机测试过了，可以记为“据你描述已验证”，除非系统确实拿到可核查的测试证据。

## 扫描时机

当前倾向是在工作重入、用户明确同步进展或相关视图打开时按需增量观察；可选轻后台更新后置。不要无界递归扫描所有仓库，不要让大 monorepo 扫描阻塞 DSH。

## 未提交变化的历史

用户希望回顾时能够看到当时的实际内容，而不只是文件名与时间，并希望 DSH 在适当时机帮助 commit。建议分阶段实现：

1. 先发现工作树、未跟踪文件和 diff 摘要。
2. 对选中工作范围内的普通文本，按明确保留规则保存有限快照或可恢复差异。
3. 对敏感路径、凭据、大型二进制和不适合存档的文件应用明确排除/保护规则。
4. DSH 可建议提交、准备提交说明或执行已授权的 commit；不强制用户为每个阶段手工 commit，也不自动把 commit 等同任务完成。

存储承诺仍需明确：用户倾向“都能看到”，但“保存所有文件的完整历史”会涉及容量、隐私和敏感信息。初期应限定选中工作目录与文件类型，并在界面清楚说明哪些内容被保存、保存多久以及哪些内容无法恢复。

## 结构历史

历史视图默认显示“今天的项目工作结构”，用户选择时间段后向前回看。它不是阶段卡片或 Git 提交消息列表，而是在同一张结构图上呈现：

- 节点新增、删除、改名和描述变化。
- 父子归属与依赖关系变化。
- 正式状态变化。
- 能够关联到的 Logseq 原文、Git diff、Kernel 收据和 DSH 证据。

正式对象树、Logseq 来源树和代码模块图必须是可切换/对照的不同投影，不能强行融合成一张万能真相图。节点身份稳定时尽量保持位置；只移动受影响节点，避免每次拖动历史滑块就整图重排。

历史原文缺失时，仍显示能证明的节点与关系，但明确说“当时原文未保存”。不得用今天的描述补写旧帧，更不得让 AI 编造合理的历史标题。

## 阶段标题

自动提炼的阶段名称只是可编辑的回顾书签，不成为需要维护的正式阶段实体。正式意义、用户认可的回顾和工作状态变化另行记录。

## 从旧结构恢复

用户倾向允许从旧结构选择需要恢复的变化，生成针对今天的草案，而不是把整棵树回滚到旧版本。因为当前项目可能已有新任务，恢复时要把旧变化与当前基线比较，处理冲突后再形成可审阅差异。

这一能力依赖历史版本、当前对象身份和冲突处理，建议放在只读历史 MVP 之后；不应为了让首版看起来完整而伪造恢复能力。

## 验收标准

1. 可以观察 DSH 之外的 Git/文件/Logseq 变化，包括未提交与未跟踪内容的基本存在。
2. 观察与解释分开；“无变化”“未观察”“无法访问”是不同状态。
3. 用户补充意图后能关联已有工作，不强迫新建 Task。
4. 历史滑块改变真实节点、文本、归属与依赖；稳定节点位置尽量保持。
5. 可切换正式对象树、Logseq 来源树和代码模块图；来源可核查。
6. 缺失历史明确显示未知，不以当前内容填补旧历史。
7. 旧结构恢复先生成针对当前版本的草案，绝不直接整树回滚。
8. 快照范围、敏感文件策略和存储保留规则明确可检查。
