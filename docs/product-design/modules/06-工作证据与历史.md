## 1. 产品定位

Work Evidence 不应只是一款 Git
状态浏览器，也不应只是一个要求用户手动填写工作日志的表单。它的目标是：**用户自然工作一段时间后，系统主动观察可获得的工作证据，由
Agent
尝试还原工作内容，只在关键处向用户澄清，最终形成可追溯、可继续使用的工作交接记录。**

典型入口是用户回到 DSH
后点击"同步一下我刚才做的事"。系统从上次同步到当前时点收集可观察变化，逐条分析，必要时提问，最终将结果保存到
Work Evidence 历史，并允许用户把记录引用到 DSH 原生草稿。

## 2. 要解决的问题

用户在 IDE、终端、Codex、DSH
或其他工作环境中自然推进工作时，通常不会同步维护一份完整日志。工作结束后，用户需要自行回忆目标、翻查
Git Diff、寻找相关上下文、判断哪些检查真正运行过，再把信息整理成下一轮
Agent 能理解的说明。

Work Evidence 应减少这类重复整理工作，尤其应降低： -
从文件变化中还原工作意图的成本； - 手动整理阶段总结和工作交接的成本； -
下次恢复工作时重新阅读历史的成本； - 把不确定推断误写成确定事实的风险。

## 3. 已确认的产品决策

以下为用户明确选择的设计基线，不应在实现时被悄然替换：

1.  **同步范围：** 从上次同步到现在，包含新 Git 提交与当前未提交变化。
2.  **条目组织：** 先按文件呈现，再由 Agent
    根据工作目的归组；分组不得丢失文件级证据和 Diff 引用。
3.  **分析上下文：** 除 Git 变化外，允许结合当前工作区关联的 DSH
    会话、Logseq 工作结构等相关上下文。
4.  **澄清策略：** 只对影响结论的少量关键不确定性提问，用户可以跳过。
5.  **交接记录：** 保存到 Work Evidence 历史，并可引用到 DSH 草稿。
6.  **结构视图：**
    默认使用清晰的条目列表，必要时切换结构视图；不同模块应共用底层结构可视化工具。

## 4. 核心用户旅程

1.  用户在日常环境中自然工作，不必预先创建工作阶段或填写日志。
2.  用户回到 DSH，点击"同步一下我刚才做的事"。
3.  系统根据上次同步检查点和当前仓库状态，发现新提交与当前工作区变化，形成文件级条目。
4.  Agent 对条目进行分析，逐条显示进度，并以自然语言解释可观察到的变化。
5.  Agent
    识别可能属于同一工作目的的文件，将它们归组；用户仍可展开查看每个文件。
6.  只有在某个关键不确定性会影响工作目的、结果或下一步时，才向用户提出简短问题。
7.  用户回答、编辑解释或跳过问题。回答后只重新分析受影响的条目或工作组。
8.  用户认为信息已经足够时，生成并保存工作交接记录。尚未确认的内容保留为未知或待确认。
9.  用户可查看历史记录、编辑交接文本，并将其引用到 DSH
    原生草稿；系统不自动发送消息。

## 5. 功能需求

### 5.1 同步与观察

-   以仓库为范围维护上次同步检查点。
-   后续同步覆盖检查点之后的新提交，以及当前暂存、未暂存、未跟踪、删除或重命名等可观察的工作区变化（具体
    Git 能力以实际仓库适配能力为准）。
-   能区分新提交、当前工作区状态和历史观察记录。
-   避免同一项变化仅因从未提交状态转为提交状态而被无意义地重复呈现。
-   首次同步没有历史检查点时，应明确说明它是初始观察，不假装知道更早发生的工作。
-   不自动创建 Git commit，不修改用户仓库内容。

### 5.2 文件条目与工作主题

-   首先提供具体文件级条目，显示路径、变化类型及可用的差异信息。
-   Agent 可以将多个文件归组为一个更高层的工作主题。
-   每个工作主题必须保留其下属文件和来源引用。
-   不要求一文件永远对应一项工作：后续可在有证据支持时识别跨文件的共同目的。
-   归组属于 Agent 的解释，不得改写原始观察事实。

### 5.3 Agent 分析

-   Agent 为每个条目生成简明、自然语言的变化解释。
-   条目应有局部进度与结果状态；一个条目的分析不应阻塞其他条目查看。
-   分析解释应基于实际可读取的 Diff、文件上下文和允许的关联来源。
-   无法确认的内容应表达不确定性，不能把推测写成事实。
-   分析完成只代表已形成解释，不代表工作已完成、测试已通过或任务已正式关闭。

### 5.4 相关上下文

-   可以使用当前工作区明确关联的 DSH 会话、Logseq 工作结构和相关记录。
-   上下文应与当前工作有可说明的关联，避免无边界地扫描所有历史会话或无关项目。
-   UI 或交接记录应能区分 Git 等来源直接观察到的事实、Agent
    的解释和用户补充。
-   无法读取或不存在的上下文不得伪装成已检查。

### 5.5 澄清问题

-   只在不确定性会影响工作目的、结果、验证情况或下一步时提出问题。
-   优先提出少量、具体、容易回答的问题。
-   允许用户回答、编辑已有解释或跳过。
-   回答后只重新分析受影响的条目或工作组。
-   用户跳过问题时仍可继续生成交接记录；未确定内容应保留为未知、待确认或未验证。
-   不要求用户回答全部问题才能结束同步。

### 5.6 工作交接记录

交接记录的目标是帮助下一次工作或下一位 Agent
恢复上下文。可根据实际证据组织以下内容，不要求每一项都强行填满：

-   工作主题和时间范围；
-   本次工作目标（有证据或用户说明时）；
-   主要变化及对应文件/来源；
-   Agent 的解释和用户确认；
-   实际执行且有结果证据的验证；
-   未解决问题、未知事项和阻塞；
-   建议的下一步；
-   来源引用与生成时间。

交接记录应保存到 Work Evidence
历史，并可被重新打开。用户可以检查、修订记录，再将其引用到 DSH
草稿。引用与发送必须分离。

### 5.7 结构视图与前端体验

-   默认采用清晰、易扫描的条目列表。
-   当工作组、文件关系或依赖值得整体理解时，允许切换到结构视图。
-   复用项目内共享的结构可视化工具；Work Evidence
    提供自己的数据适配，不依赖整个结构历史业务模块。
-   关键状态应自然可见：分析中、已形成解释、需要澄清、重新分析中、存在错误或未完成。
-   避免不必要的按钮、重复信息、技术术语和复杂表单。
-   用户应能在其他条目仍分析时查看已完成结果。

## 6. 信息语义与信任边界

系统至少区分以下四类内容：

1.  **观察事实：** Git、文件、测试工具等实际返回的结果及来源。
2.  **Agent 解释：** Agent 对变化目的、关系和意义的理解。
3.  **用户澄清：** 用户补充或修订的意图、目标和结果说明。
4.  **工作交接记录：** 汇总前三者的可继续使用的工作产物。

这些信息有关联，但不能相互替代。Git 有变化不代表任务完成；Agent
分析完成不代表验证通过；用户跳过澄清不代表系统可以补造确定性。

## 7. 明确的非目标

本阶段不要求： - 自动创建或完成 Formal Kernel 任务； - 自动写入 Logseq
Graph 或正式 Kernel Evidence； - 自动发送 DSH 消息； - 自动执行 Git
commit； - 实现完整 Git 历史浏览器； - 让所有条目都必须显示结构图； -
为所有理论异常建立复杂的通用状态机或抽象平台。

## 8. 体验验收原则

至少应能实际完成： - 首次同步与后续增量同步； -
同时包含新提交和未提交变化的观察； - 文件级条目、Agent
解释与工作主题归组； - 某个条目需要澄清，回答后局部重新分析； -
跳过问题后仍能生成保留未知项的交接记录； - 保存并重新打开交接记录； -
引用交接记录到 DSH 草稿但不自动发送； -
默认列表与可选结构视图之间切换； -
分析失败或来源不可用时仍能保留已获得的证据与用户输入。

最终验收应以真实 DSH
宿主的实际交互为依据，不能仅以单元测试或独立演示页面代替。

## 结构历史

历史视图默认显示“今天的项目工作结构”，用户选择时间段后向前回看。它不是阶段卡片或 Git 提交消息列表，而是在同一张结构图上呈现：

- 节点新增、删除、改名和描述变化。
- 父子归属与依赖关系变化。
- 正式状态变化。
- 能够关联到的 Logseq 原文、Git diff、Kernel 收据和 DSH 证据。

正式对象树、Logseq 来源树和代码模块图必须是可切换/对照的不同投影，不能强行融合成一张万能真相图。节点身份稳定时尽量保持位置；只移动受影响节点，避免每次拖动历史滑块就整图重排。

历史原文缺失时，仍显示能证明的节点与关系，但明确说“当时原文未保存”。不得用今天的描述补写旧帧，更不得让 AI 编造合理的历史标题。

## 阶段标题

自动提炼的阶段名称只是可编辑的回顾书签，不成为需要维护的正式阶段实体。正式意义、用户认可的回顾和工作状态变化另行记录。

## 从旧结构恢复

用户倾向允许从旧结构选择需要恢复的变化，生成针对今天的草案，而不是把整棵树回滚到旧版本。因为当前项目可能已有新任务，恢复时要把旧变化与当前基线比较，处理冲突后再形成可审阅差异。

这一能力依赖历史版本、当前对象身份和冲突处理，建议放在只读历史 MVP 之后；不应为了让首版看起来完整而伪造恢复能力。

## 结构历史与来源保留验收（沿用）

1. 可以观察 DSH 之外的 Git/文件/Logseq 变化，包括未提交与未跟踪内容的基本存在。
2. 观察与解释分开；“无变化”“未观察”“无法访问”是不同状态。
3. 用户补充意图后能关联已有工作，不强迫新建 Task。
4. 历史滑块改变真实节点、文本、归属与依赖；稳定节点位置尽量保持。
5. 可切换正式对象树、Logseq 来源树和代码模块图；来源可核查。
6. 缺失历史明确显示未知，不以当前内容填补旧历史。
7. 旧结构恢复先生成针对当前版本的草案，绝不直接整树回滚。
8. 快照范围、敏感文件策略和存储保留规则明确可检查。
