# 模块需求：Proposal as Diff 与正式操作

> 状态：产品设计工作基线，非已实现能力清单。下文方案与验收目标受[来源与状态](../SOURCE-AND-STATUS.md)及[待决登记](../DECISION-REGISTER.md)约束；未标定的实现细节按设计建议理解，倾向和未回答均不构成最终决定。返回[文档导航](../INDEX.md)。

## 目标

用户不应被要求阅读一篇 AI 小作文，才能知道 Agent 改了什么。变化应当出现在发生变化的上下文附近，默认清晰、短小、可核查，并允许直接执行用户明确指令。正式写入需要尊重 Kernel 既有权威语义，但不能把每个普通操作都变成重复审批。

## 两条操作路径

### 用户明确指令

当用户在可信 DSH 会话中明确说“把当前任务改名为……”，目标唯一、操作范围明确且在授权内时，建议直接执行并回复一行结果；提供“查看修改记录”入口。若用户明确指出三项已完成，可记录这是用户的完成判断，而不是因为系统未看到测试就擅自否决。

### Agent 自主建议

当 Agent 自己推断“这个任务应该完成”“最好同时重写另一个项目”时，不能假装用户已经指令。它应给出简短、可操作的差异和来源，等待适当的用户决定。

## 需要更强确认的情况

- 不可恢复删除或覆盖不可恢复的用户材料。
- 扩大读取/写入权限，特别是越出当前工作范围。
- 修改其他项目或跨工作区执行未授权变更。
- 向外部对象发送内容、发布、提交外部承诺。
- 目标含糊、对象不唯一，或操作会产生明显超出用户原指令的影响。

风险不应简单由“改了多少文件”决定。一个重命名可能很低风险；一个小操作也可能泄露凭据或改变正式生命周期。

## Diff 的默认呈现

- 默认一句结果或一句理由。
- 旧值 → 新值；涉及结构时，在同一张图上高亮增删移动。
- 变化依据和来源入口。
- 影响范围：哪些正式对象、父级、依赖或投影受到影响。
- 可选择接受、拒绝、修改或局部采纳。
- 详细依据按需展开，不把模型内部推理全文当成审计证据。

DSH 的工具结果旁只放轻量入口；只有用户打开审阅时才呈现完整 Diff，避免把中央对话滚动区塞满大卡片。

## 局部采纳和冲突

- 多项变化可以分别选择。
- 若接受子节点但拒绝其必要上级，保留用户选择并说明缺少哪个上级，提供重新选择归属，而不是静默改动。
- 审阅中如果同一对象被其他端修改，保留未受影响的勾选和评论，只把冲突项标出并要求重新检查。
- 不用过期基线无限重试。

## 操作结果必须可读

至少区分：已保存轻量记录、正式操作已接受、部分完成、发生冲突、结果暂时未知、已取消/停止后续操作、Graph 投影待处理/冲突。

Kernel 正式事实已接受而 Logseq Graph 还未更新时，应明确显示两者状态；不能把投影失败说成正式操作失败，也不能把正式接受说成整个同步链已完成。

## 异步与停止

每个正式操作使用稳定请求身份，允许查询原收据和幂等重试。网络超时不等于操作失败；再次点击不应自动创建新操作。

用户说“停一下”时，立即停止后续派发，查询在途操作的结果后再说明。已经派发的操作不一定可撤销；界面不能承诺“关闭窗口就取消所有后端动作”。

## 撤销

轻量视图状态、工作集和 Inbox 队列操作应容易撤销。已经接受的正式操作不能被普通的“撤销捕获”悄悄回滚；如需反向正式变更，应走独立、可追溯的补偿操作。

## 验收标准

1. 明确、可信、范围内的用户指令可以直接执行，无不必要的第二次确认。
2. Agent 推断不冒充用户指令；越界扩范围先停下说明。
3. Diff 以真实变化和来源为核心，默认短、可读、可局部采纳。
4. 结构变化可通过图形表达，目录/清单作为稳定回退。
5. 部分成功、冲突、未知回执和投影待处理都可区分。
6. 重试不会造成重复正式操作；停止不会谎称撤销在途副作用。
7. 用户能查看操作记录，但日常界面不暴露内部编码。

## 待明确

- 可信 DSH 用户指令如何传递到 Kernel：需基于宿主真实 API 设计，不接受 Agent 自填来源字段作为信任根。
- 不同正式操作的确认策略如何分级：先建立最小分类，不建设通用审批引擎。
