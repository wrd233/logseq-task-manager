# Task Copilot：产品总览与共同设计原则

## 1. 一句话定义

Task Copilot 是一个以 DSH 原生 Agent 对话为主要工作现场、以 Logseq 保存自然材料、以 Formal Kernel 维护正式工作事实，并把外部工作证据、历史结构、个人投入节奏与工作接续连接起来的个人工作系统。

它不是要重做笔记软件、IDE、通用日历或万能 Agent UI。它要解决的是：**工作跨会话、跨工具、跨时间推进时，人不必重复解释背景、手工维护每个阶段，也不会因为 AI 的推断而失去对正式事实的控制。**

## 2. 用户真正想省掉什么

最昂贵的不是少点几次按钮，而是反复重建上下文、辨认不可信的摘要、把零散想法强行分类、手动汇报工作进展，以及在不同尺度的界面之间往返后丢失原现场。

因此，系统的主要价值不是制造更多任务、建议或评分，而是：

- 随手想起一件事时，先可靠留下它，然后立刻回到原工作。
- 回到工作时，知道上次停在哪里，相关材料后来发生了什么变化。
- 需要调整结构时，能直接看见真实的节点、归属、依赖和变更差异。
- DSH 明确接到指令后可以积极执行；Agent 自己推断的结论不自动成为正式事实。
- 对 DSH 之外发生的工作，也能从 Git、文件、Logseq 和用户简短补充中建立有依据的记录。
- 日程帮助人安排现实投入，不反过来把人变成计时器和日清表的维护者。

## 3. 系统中的四种角色

### DSH：正在做事的地方

DSH 原生对话、模型和工具调用是主要工作现场。Task Copilot 不应重建另一套聊天界面，也不应在对话中央长期堆放大型任务面板。需要阅读原文、看文件或调整结构时，应按需打开相应的视图，完成后能返回原对话。

### Logseq：自然材料与长期笔记

Logseq 继续保存自然语言、原始笔记、Journal 和可由人自由编辑的材料。不要要求每条想法都成为 Task，也不要让系统把推断直接写成正式事实。

### Formal Kernel：正式事务事实

Kernel 维护正式工作对象、归属、生命周期和有权威来源的正式操作。前序固定版本核查确认的当前正式对象基线是 `Task / MiniProject / Project`；实现开始时需重新核对当前 schema 与代码，不能把设计讨论中的 Area、Decision、Output 等名称当作已实现类型。

### Git 与文件系统：工作发生过什么的证据

Git、未提交变化、工作目录与 Logseq Graph 能帮助回答“哪些材料改变了”。它们不能单独证明“目标已达成”。用户补充的意图、验证与决定应和机器观察分开记录。

## 4. 三个工作尺度

1. **工作现场**：我现在在哪里继续？主要在 DSH 对话中，围绕当前意图、来源和工具结果工作。
2. **工作结构**：这些任务、项目和依赖怎样关联？默认以可展开的文字目录为主，需要分析时进入结构图。
3. **投入节奏**：接下来愿意把哪段时间用于什么工作？以语义时段和一次投入为单位，不要求所有事情先拆成 Task。

跨尺度切换应保留工作身份、原 DSH 会话、未发送草稿、选中来源和返回点。改变浏览对象不等于改变 Agent 的执行目录或授权范围。

## 5. 共同设计原则

### 原则一：当前界面只强调当前行为

捕获时突出输入；恢复时突出上次工作位置；审阅时突出真实变化；日程调整时突出可拖动的投入；收尾时突出结构变化、遗留点和下次入口。不要让所有状态、说明和按钮同时争夺注意力。

### 原则二：短说明、可读命名、按需展开

日常界面不暴露内部 ID、Git 哈希、复杂枚举或含糊的架构术语。需要诊断时可在详情或复制信息中提供内部值。信息密度来自准确内容和稳定层级，而不是塞满屏幕或叠加大量字号。

### 原则三：明确委托要积极执行，推断不要冒充指令

明确、可信、目标清楚且处于授权范围内的用户指令，尽量直接执行并简短汇报。Agent 自主提出的正式变化，或会扩大范围、影响其他项目、不可恢复删除、对外发送和形成外部承诺的操作，应提高确认强度。不能仅凭模型写入的“用户授权”字段冒充可信用户来源。

### 原则四：轻量记录不必是正式工作对象

Capture、Inbox 处理状态、阅读位置、工作集、日程草案和主题偏好属于运营/视图状态。它们可以引用正式工作身份，但不应全部升级成 Kernel WorkObject。正式化发生在有明确事务意义且具备必要来源条件时。

### 原则五：Proposal as Diff，而不是 AI 小作文

把提案放在发生变化的上下文附近。默认显示短说明、旧值到新值、来源和影响范围；详细依据按需展开。允许局部采纳、拒绝、编辑和重新审阅。没有可靠线索时允许零条建议。

### 原则六：结构图是一种共享表达，不是新的万能工作台

同一结构表达能力可以用于拆解、正式变更预览、历史回放、恢复、暂停、收尾和领航提示。默认只聚焦当前工作及邻域；不做一张把所有对象、聊天、标签、文件和依赖一次画全的毛线球。

### 原则七：动画只表达真实状态变化

Capture 的光点只能在实际持久化后出现；结构节点的高亮应对应真实工作位置或真实差异；动画不能替代保存收据、授权或失败说明。支持减少动效，保持稳定的可读回退。

### 原则八：自然工作尽量不断，正式写入必须诚实

DSH、Kernel 或 Graph 暂时不可用时，仍尽量允许用户查看可用材料、捕获想法和补充意图。若正式操作无法被权威接受，不能显示为成功；若 Kernel 已接受而 Graph 投影未完成，要清楚显示“正式记录已接受，Logseq 更新待完成”。

## 6. 核心使用路径

### 路径 A：一句想法

呼出 Capture → 直接输入 → 可靠保存 → 收起并恢复原工作 → 日后在 Inbox 搜索/编辑/处理 → 视意图保留为想法、写入 Journal、带去 DSH 或正式化为工作对象。

### 路径 B：恢复一项工作

从 DSH 工作入口进入 → 在同一结构图中高亮上次工作位置和上次之后的相关变化 → 打开来源或原生会话 → 继续推进。旧停点失效时，先给出可用材料和重新定位入口，不装作原链接仍有效。

### 路径 C：调整工作结构

在目录或结构图中定位 → 拖动节点或提出结构变化 → 先看同一张图上的增删移动和文字差异 → 局部采纳或重新选择归属 → 正式写入按权限执行 → 显示收据与 Graph 投影状态 → 回到原处。

### 路径 D：外部工作回顾

用户回到项目或明确要求同步进展 → 按需观察 Git、文件与 Logseq 变化 → 显示可核对证据 → DSH 根据实际缺口提出少量动态追问 → 保留用户意图与机器观察的区别 → 可选写入 Journal 或更新正式对象。

### 路径 E：有限领航

用户指定工作范围和停点 → 系统用结构图高亮本轮目标并准备合适的会话入口 → 在范围内连续执行低风险、机器可完成的小步骤 → 人类决策点停下来等用户继续 → 随时暂停或结束 → 用同一结构图总结本轮变化、遗留点和下次入口。

## 7. 产品范围

### 近期核心

- DSH 中快速捕获、可编辑 Inbox、搜索、归档、带引用进入 DSH、无损返回。
- DSH 工作入口、来源阅读层、工作身份与会话绑定的清晰表达。
- 真实工作结构历史的只读回放与来源核查。
- 基础目录/结构图、局部 Diff 和正式写入结果说明。
- 从 Git/文件/Logseq 观察外部变化，并在 DSH 对话中补齐缺失意图。
- 语义时段规划和基础有限领航边界。
- 轻像素主题作为可插拔外观，不改变数据与行为。

### 暂不作为初期目标

- 全面替代 Logseq、DSH、IDE 或日历。
- 永久在线扫描所有工作目录并自动读取所有私密内容。
- 默认 AI 相似聚类、自动跨项目优先级、健康分数或生产率评分。
- 完整 RPG 任务地图、剧情系统、可编辑大型世界地图。
- 复杂通用工作流引擎、过多独立持久实体或多套并行正式数据库。
- 无期限自治或无边界正式写入权限。

## 8. 成功与失败的判断

关注的是是否减少真实认知成本：首次捕获是否无需教程、保存是否可靠、是否能回到原焦点、Inbox 是否容易找到与编辑、恢复时是否更快理解停点、Diff 是否可读、是否出现错误正式化、跨项目串线、重复操作或无法恢复的写入。

不以任务数量、AI 使用次数、连续签到、专注分钟数或虚构的“项目健康度”作为核心成功指标。
