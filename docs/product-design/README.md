# Task Copilot 产品设计基线

> 版本：Draft 0.1 · 依据截至 2026-10-20 的多轮设计讨论与 Grill Me 反馈整理。本文档包是产品/实现工作基线，不代表每项行为都已最终确认，也不表示所述功能已在仓库实现。

## 仓库维护入口与权威范围

先读[来源与状态](SOURCE-AND-STATUS.md)、[待决登记](DECISION-REGISTER.md)和[产品总览](01-产品总览.md)，再按[导航](INDEX.md)进入模块与跨模块设计。

- `modules/` 下九份独立文档是各模块产品需求的日常维护权威来源；总览负责共同原则，跨模块设计负责共享边界。冲突应登记并澄清，不能静默覆盖。
- 来源与状态规则、待决登记约束所有模块；文档中的验收条款是候选产品目标，仍受原始 `leaning` / `unanswered` 状态限制。
- 实施安排是后续开发的参考建议，不是当前开发授权，也不证明 DSH 调用通道或宿主能力可用。本次仅建立文档基线。
- 现有正式架构/API/ADR 与源码继续说明实现事实；本目录不替代它们。本文提及的代码能力来自前序固定版本研究，本轮没有重新验证业务能力。
- 不入库合订本，避免双份权威正文；如将来生成合订本，必须标明为从独立文档生成的阅读快照，修改回到独立文档。
- 原始反馈、完整研究上下文和原型留在本地；仓库仅保留[来源类别与追溯记录](sources/README.md)。

Capture / Inbox 与结构历史的后续并行开发，先读[实际代码基线](planning/00-代码基线核查-2026-10-21.md)末节与[共同契约](planning/02-并行开发契约.md)，再使用其中两份 Goal。本次刷新只发布最小共享类型、独立检出方式和任务边界，不启动功能实现，也不改变本套产品文档的倾向/待决状态。两条分支从同一共同基线开始；真实宿主接线由共同基线主代理串行完成。

## 如何读

- 先读产品总览，理解产品要解决的问题与不做什么。
- 再读 Capture/Inbox、DSH 工作现场、接续收尾、工作结构、证据历史等模块。
- 然后读跨模块设计；它解释模块之间如何共享工作身份、结构图、授权、返回现场和操作结果。
- 最后读实施安排。Codex / DSH 应按其中的依赖与责任边界分工，不应把所有模块同时重写。

## 状态标签

- **[用户方向]**：用户直接写下的偏好或修正；即使强烈，也不自动等于最终接受的产品决定。
- **[当前倾向]**：反馈 JSON 中的 `leaning` 选择或方案。
- **[代码基线]**：前序对固定仓库版本的核查结果；开工前必须重新核对当前 HEAD 与工作树。
- **[设计建议]**：本套文档提出的推荐实现方式。
- **[待明确]**：缺少决定或需真实宿主/使用样本验证。

本轮反馈共有 91 道问题：74 道为 `leaning`、17 道为 `unanswered`，没有任何回答标记为 `accepted`（入库时核对 ZIP 内反馈状态）。因此本文档有意使用“工作基线 / 当前倾向 / 推荐默认”，不把它们写成已签署的最终决定。

## 重要边界

- 本次仅新增本目录产品文档；不开发功能，不修改业务代码、配置、依赖、根 README 或现有正式架构文档。
- 原型不是现有实现的证明。当前 DSH 宿主行为、SDK 插槽和两个分支差异须在实施开始时重新检查。
- 既有研究的固定基线曾记录 `main` 与 `codex/one-click-dsh-collaboration` 的 SHA；实现代理应重新读取当前 SHA，而不是盲用旧结论。
- 正式 Kernel 写入与 Logseq Graph 投影不是同一个结果：正式提交被接受后，Graph 投影仍可能待处理或冲突。用户界面必须说清状态。
- DSH 的浏览、执行目录、工作身份、读取授权、模型上下文投递是不同概念，不得用一个下拉框或一个布尔值混为一谈。
