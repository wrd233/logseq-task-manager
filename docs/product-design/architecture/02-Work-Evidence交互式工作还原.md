# Work Evidence：交互流程与架构设计

> 2026-10-22 产品设计基线。关联权威需求：[模块 06](../modules/06-工作证据与历史.md)。这是目标设计，不是已实现架构；当前代码差距见[同步基线](../planning/05-Work-Evidence文档同步基线-2026-10-22.md)。通用边界继续受[跨模块设计](01-跨模块设计.md)约束。
>
> 本文中的 Structure View Toolkit 是共享能力的设计名称，并非已核实存在的公共包/API。实施前检查真实通用组件，只提取必要边界，不合入整个结构历史业务模块。Agent 上下文读取与模型投递必须遵守已有可信授权和敏感内容限制。

## 1. 设计总览

Work Evidence 的核心交互是一轮可中断、可继续的"工作还原"会话：

**同步变化 → 文件条目出现 → Agent 逐条分析 → 相关文件归组 → 按需澄清 →
局部重新分析 → 生成并保存交接记录 → 引用到 DSH 草稿。**

用户不应需要先设计任务结构或手动撰写完整总结。系统负责收集和组织证据，Agent
负责提出可检验的解释，用户负责补充只有自己知道的信息，并决定何时形成交接。

## 2. 主界面结构

### 2.1 默认视图：条目列表

同步窗口默认呈现： - 当前工作区身份与同步时间范围； -
一次同步发现的变化概览； - 文件条目列表； -
每个条目的分析状态与自然语言说明； - 需要澄清时出现的问题入口； -
生成交接记录的主要操作。

默认不要把完整
Diff、复杂结构图、技术诊断和所有元数据同时展开。文件差异、来源详情和结构关系按需查看。

### 2.2 单个条目

条目可包含： - 文件路径与变化类型； - 观察来源和时间范围； - Diff
或可用的差异摘要； - Agent 当前解释； - 解释的依据与不确定性； -
需要澄清时的问题入口； - 用户补充及重新分析后的解释。

条目解释应简明，先回答"发生了什么变化、可能意味着什么"。需要深入时再展开细节。

### 2.3 工作主题分组

初始阶段先显示文件级条目。Agent
分析后可以把多个文件归入共同工作主题，例如"修复保存竞争问题"，并将相关文件作为子项保留。

分组是解释层，不替代文件级证据。若 Agent
后续调整分组，应让用户能理解变化，不应悄然丢失已查看的条目或回答。

### 2.4 结构视图

列表是默认视图。结构视图适用于： -
多个文件或工作主题之间存在明显关系； - 需要理解层级、依赖或整体范围； -
用户主动希望从全局查看本轮工作。

结构视图必须使用共享 Structure View Toolkit 的通用能力；Work Evidence
自己负责把工作条目映射为节点和关系。结构历史专属的快照存储、修订链和历史核验逻辑不属于共享
UI 工具。

## 3. 同步检查点与观察范围

用户已选择"从上次同步到现在，包含新提交与当前未提交变化"。实现设计需要解决增量范围和重复呈现问题。

建议为每个仓库保存足以恢复上次同步边界的信息，包括当时的
HEAD、可观察的工作区状态摘要和同步时间。具体存储形式由实现决定，不要过度规定数据结构。

一次同步需要考虑： - 上次同步后新增的提交； - 当前暂存和未暂存的变化； -
新增、删除、重命名及未跟踪文件等适用状态； -
同一项变化先以未提交形式出现、后来被提交的情况； -
用户在同步后继续修改文件的情况； -
仓库无法访问、历史被改写或检查点不再可用的情况。

目标不是把每个 commit
机械地生成一条记录，而是尽可能还原自上次同步以来的工作变化，同时保留提交信息和文件级证据，避免重复堆叠相同变化。

首次同步没有前一检查点，应作为初始观察，并明确说明无法推断更早的工作。观察过程不得修改仓库内容或自动执行
Git commit。

## 4. 条目状态与局部工作流

不要求实现复杂的通用状态机，但 UI
必须表达关键状态，并允许不同条目独立推进。

建议的状态语义：

-   **待分析：** 已发现证据，尚未开始或尚未处理。
-   **分析中：** Agent 正在阅读相关内容。
-   **已形成解释：**
    当前证据足以生成可供用户阅读的说明；不代表工作完成。
-   **需要澄清：** 存在影响结论的关键不确定性。
-   **等待用户：** 问题已呈现，等待用户回答或跳过。
-   **重新分析中：** 用户回答或修改解释后，Agent 正在更新理解。
-   **可交接：**
    该条目目前已有足够的描述和来源，或剩余未知已被明确保留。
-   **分析失败/来源不可用：**
    不能完成当前分析，但保留已经获得的证据和用户输入。

一个条目完成分析，不应阻塞其他条目的查看和操作。回答一个问题后，优先只重新分析相关条目及受影响的工作主题。

允许用户提前生成交接记录。未分析、失败、跳过或仍有未知的条目不能被静默删除；在交接记录中应保留其实际状态。

## 5. Agent 分析与澄清

### 5.1 分析输入

在权限与关联范围内，Agent 可以使用： - Git 提交信息和文件变化； - 相关
Diff 与必要的文件上下文； - 当前工作区关联的 DSH 会话； - 相关 Logseq
工作结构与阶段记录； - 用户在本轮补充的信息。

上下文读取应以当前工作区及本轮变化为中心，不默认扫描所有历史会话。对每项关键解释，应尽可能保留来源引用或说明其依据。

### 5.2 分析输出

Agent 的初始说明应优先包含： - 观察到了什么； -
从代码或文件内容可以支持什么解释； - 哪些关键结论仍不确定。

不要求每条都生成长篇摘要。多个文件可在证据支持时归组，但原始文件条目仍可展开查看。

### 5.3 何时提问

仅当不确定性会显著影响以下内容时才提问： - 工作目的； -
变化的实际含义； - 是否已完成某项验证； - 尚未解决的问题； -
下一步建议。

问题应具体、简短、可回答，避免要求用户重复系统已经能够观察到的信息。用户可回答、编辑解释或跳过。

### 5.4 回答后的更新

回答应与提出问题的条目或工作主题关联。Agent
重新分析受影响的内容并更新解释，同时保留： - 原始观察事实； -
用户提供的澄清； - 当前解释； - 仍未解决的不确定性。

不能因用户回答一个问题就无条件重跑整轮同步，也不能静默改写原始观察记录。

## 6. 工作交接记录

交接记录是本轮工作还原的主要产物。用户认为信息足够时可生成，不要求所有条目都达到"完全理解"。

建议的内容结构：

1.  **工作主题与时间范围**
2.  **本轮主要目标**（来源明确时）
3.  **已观察到的主要变化**，按工作主题组织并保留文件引用
4.  **验证情况**：区分实际运行并有结果的检查、未运行的检查、Agent 推断
5.  **用户澄清和重要决定**
6.  **未解决问题、阻塞和未知**
7.  **建议的下一步**
8.  **来源与生成时间**

根据实际证据选择内容，不要强行填满每个栏目。未验证的结果不能写成"测试通过"；未回答的问题不能被自动补全为确定答案。

交接记录保存到 Work Evidence
历史，可重新打开。用户应能检查和修订内容，并将记录引用到 DSH
原生草稿。引用、发送、正式任务创建和 Graph
写入是不同操作，不能隐式合并。

## 7. 数据语义

建议在概念层区分：

-   **Observation：** 某次同步获得的原始工作观察和来源；
-   **File Item：** 从观察中形成的文件级条目；
-   **Work Group：** Agent 对相关条目的工作目的归组；
-   **Interpretation：** Agent 基于证据形成的解释；
-   **Clarification：** 用户回答或修订；
-   **Handoff Record：** 由观察、解释和澄清整理出的交接产物。

这些名称是设计概念，不要求机械地一一创建独立数据库表。实现应复用现有
Work Evidence 存储结构，只有在现有模型无法表达必要语义时才扩展。

原始观察不可被 Agent
解释覆盖。交接记录可以被用户编辑，但应保留必要的来源关系，避免编辑后失去可追溯性。

## 8. 与共享结构可视化工具的关系

目标架构应分为两层：

### 共享工具层

负责通用结构呈现能力，例如： - 节点与关系的展示模型； - 布局和渲染； -
选择、聚焦、展开和详情交互； - 通用的视觉状态和结构差异呈现。

### 业务适配层

-   Structure History 将已核验的阶段快照和修订差异转换为结构视图输入。
-   Work Evidence 将文件条目、工作主题和有依据的关系转换为结构视图输入。

共享工具不应负责 Git 观察、AI
分析、工作分组、历史快照存储或正式任务状态。不要为了复用图形界面而让
Work Evidence 依赖整个 Structure History 模块。

在核查最新代码后，先复用已有的独立组件或提取最小共享边界。不要在设计阶段凭空指定一个与实际仓库不符的组件
API。

## 9. 前端设计原则

-   默认列表，结构图按需出现。
-   先展示变化与解释，再展开技术细节。
-   每条目独立反馈分析进度。
-   问号只用于需要用户澄清的条目，不作为装饰。
-   提问、回答、跳过和重新分析应在局部完成。
-   用户可以继续浏览其他条目，不被全局加载状态阻塞。
-   允许提前交接，不强迫完成所有问题。
-   保存状态、未解决事项和验证状态清晰可见。
-   减少按钮、冗余状态、重复校验和不必要的技术术语。
-   这是个人项目，不构建过度通用的框架或复杂防御层；保留保护用户输入、避免覆盖记录和防止越界写入所必需的安全性。

## 10. 验收场景

设计应能够指导后续验证以下场景：

1.  首次同步并明确初始范围。
2.  上次同步后出现多个新提交，同时当前工作区仍有未提交变化。
3.  多个文件被 Agent 归为同一个工作主题，仍可查看各文件 Diff。
4.  一个条目正在分析时，用户可以查看另一个已完成条目。
5.  Agent 对关键目的不确定，提出一个简短问题。
6.  用户回答后，只有相关条目重新分析并更新解释。
7.  用户跳过问题，仍能生成保留未知项的交接记录。
8.  分析失败或来源不可用时，已有观察与用户输入仍保留。
9.  交接记录保存后可以重新打开，并引用到 DSH 草稿。
10. 用户能在列表和结构视图之间切换，且两种视图表达同一批工作条目。
11. 交接记录不会把 Agent 推断伪装成实际验证结果。
